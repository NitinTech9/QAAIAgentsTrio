# Pull Request Generator

You take the current branch's changes from working tree to open PR in one command: generate the
title/description, then (after confirmation) **stage, commit, push, and create the PR**. The commit
is gated by the repo's pre-commit hook, so the no-5xx / syntax / JSON checks run as part of `/pr`.

You generate pull request titles and descriptions for the QA automation repository — a Cypress-based QA framework covering API and UI tests (optionally against more than one backend). The repo also contains AI automation tooling (agents, commands, skills) that generate test cases from Jira tickets.

The conventions below come from merged PRs and project structure. Follow them — do not invent extra structure.

## Instructions

1. **Analyze the current branch and changes:**
   - Get the current branch name and extract the Jira ticket (see "Jira Ticket Extraction" below).
   - Determine the parent branch using this priority order:
     1. If the user passed an argument, use it.
     2. Auto-detect via `git merge-base` — this repo uses `main` as the default branch (`origin/HEAD` points there).
     3. If detection fails, ask the user.
   - Review commits and file changes since diverging from the parent branch.

### Parent Branch Detection Commands

```bash
# This repo integrates into main
git merge-base HEAD main >/dev/null 2>&1 && echo "main" ||
git merge-base HEAD master >/dev/null 2>&1 && echo "master"

# Commits since parent branch
git log --oneline <parent>..HEAD

# File changes since parent branch
git diff <parent>..HEAD --name-only
git diff <parent>..HEAD --stat
```

When scanning the diff, flag any of these areas — they affect what goes into the Summary and Test Plan:

- `cypress/e2e/API/<module>/` — API test specs (note which modules are affected)
- `cypress/e2e/UI/<module>/` — UI test specs
- `cypress/e2e/pages/` — Page Object files (affect multiple UI tests)
- `cypress/support/commands.js` — custom Cypress commands (shared across all tests)
- `cypress/support/dataFactory.js` — test data generators
- `cypress/tasks/` — DB task files (`queryDb`, `querySecondaryDb`, etc.)
- `cypress/fixtures/` — test data, request bodies, swagger specs
- `cypress/fixtures/schemas/` — JSON Schema validation files
- `cypress.config.js` — Cypress configuration (timeouts, env vars, plugins)
- `.claude/commands/`, `.claude/agents/`, `.claude/skills/` — AI automation tooling
- `.claude/project-config.json` — agent/command configuration
- `docs/test-cases/` — manual test case files (generated by agents)
- `docs/.ticket-context/` — ticket context files (generated by agents)
- `postman/collections/` — Postman collection files
- `AI-AUTOMATION-GUIDE.md` — automation documentation
- `package.json`, `package-lock.json` — dependency changes

2. **Generate the PR title.**

   Use a clear, descriptive title. If the branch has a Jira ticket, lead with it in brackets. Keep under 70 characters.

   ```
   [PROJ-XXXXX] <concise description>
   ```

   - Use imperative mood ("Add", "Fix", "Update", "Remove" — not "Added", "Fixed")
   - If no Jira ticket is associated, describe the change directly (e.g. "Add schema validation for contracts API")
   - For multi-module work, name the primary module or say "multiple modules"

   Examples:
   - `[PROJ-16917] Add order refund API tests`
   - `[PROJ-17350] Add checkout page discount radio button tests`
   - `[PROJ-17309] Add subscription cancellation export automation`
   - `Add schema validation for all API modules`
   - `Fix failing checkout flow test selectors`
   - `Update AI automation agents and pipeline commands`

3. **Generate the PR body.** Use only the sections below. Omit any that don't apply — do not pad.

### Required Sections

```markdown
## Summary

- One bullet per distinct change. Lead with what was tested or automated, not implementation detail.
- Reference test modules, spec files, and endpoints in backticks.
- For agent/command changes, describe the behavior change.

## Modules Affected          (include when test specs changed)

List the cypress test modules touched (e.g. `orders-module`, `users-module`, `admin-module/settings`).

## What's NOT changing       (optional — include only if scope is easy to misread)

Short clarification of related tests intentionally left alone, to head off reviewer questions.

## Test plan

- [ ] `npx cypress run --spec "<changed-spec-file>"` passes locally.
- [ ] For API tests: the backend under test is running and test data exists.
- [ ] For UI tests: app is running and tests pass in headed mode.
- [ ] For schema changes: `cy.fixture("schemas/<file>.json")` loads and validates correctly.
- [ ] For second-backend tests (if your suite has one): its base URL env var is set and its DB is accessible.
- [ ] For custom command changes: all existing tests still pass (commands are shared).
- [ ] For Page Object changes: UI tests using the Page Object still pass.
- [ ] For agent/command changes: run the affected agent against a test ticket to verify.
- [ ] No hardcoded credentials or sensitive data in committed files.

Refs: PROJ-XXXXX
```

**Trailer rules:**

- End the body with a `Refs: PROJ-XXXXX` line if a Jira ticket is associated.
- For multi-ticket PRs, add one `Refs:` line per ticket.
- The trailer block must be **contiguous** — no blank lines between trailer lines.
- Do not add `Co-Authored-By` or any "Generated with" footer to PR bodies. (Commits already carry their own trailers.)

## Jira Ticket Extraction

Branch names use either underscores or dashes after the ticket. Extract using:

```bash
BRANCH=$(git rev-parse --abbrev-ref HEAD)
TICKET=$(echo "$BRANCH" | grep -oE '[A-Za-z]{2,3}-[0-9]{4,6}' | head -n1)
```

Examples:
- `PROJ-17309_subscription_cancel` → `PROJ-17309`
- `PROJ-17350_checkout_discount_radio_button_not_working` → `PROJ-17350`
- `manualexpire` → no ticket (ask user or omit)
- `fixedfailedtc` → no ticket (ask user or omit)
- `phase12` → no ticket (ask user or omit)

If the branch name has no ticket pattern, ask the user whether to include one. Do not guess.

## Style Guidelines

- Use `-` for bullets.
- Wrap file paths, module names, endpoint paths, Cypress commands, and DB table names in backticks.
- Lead each Summary bullet with **what was tested or automated**, not implementation mechanics.
- Skip "Technical Details" / "Performance" / "Accessibility" sections — QA PRs rarely need them.
- Group changes by module when multiple modules are affected.
- For AI automation changes (agents, commands, skills), describe the user-facing behavior change.
- No Claude Code attribution footer in PR bodies.

## Workflow Process

1. **Generate PR Content** — title and description following the rules above.
2. **Present to User** — show the proposed title, description, detected base/head branches, AND the list of files that will be staged + the commit message (see "Staging & Commit"). 
3. **User Confirmation** — wait for explicit `y` before staging, committing, pushing, or creating the PR.
4. **Stage & Commit** — stage the changes and create the commit (see "Staging & Commit"). The repo's pre-commit hook runs here and gates the commit.
5. **Push Branch** — push to origin with `-u` if not already tracked.
6. **Create PR** — `gh pr create` with `--base main`.
7. **Return URL** — show the PR URL on success.

## Staging & Commit

`/pr` is the full finisher: it stages your changes, commits them (gated by the pre-commit hook),
then pushes and opens the PR. Run it after adding/editing test cases — no separate `git commit` needed.

**Branch-first guard.** First check the current branch:
```bash
git rev-parse --abbrev-ref HEAD
```
If it is `main` or `master`, **stop** and tell the user — never commit directly to the default branch:
> "You're on `main`. Create a feature branch first (e.g. `git checkout -b <ticket>-<short-desc>`), then re-run `/pr`."

**Decide whether a commit is needed.** Run `git status --porcelain`:
- If there are uncommitted changes → stage and commit them (below).
- If the tree is already clean but there are unpushed commits → skip the commit step (nothing to commit) and go straight to push + PR.

**Stage & commit:**
```bash
git add -A
git commit -m "<commit message>"
```
- **Commit message:** reuse the PR title (without the trailing period), e.g. `[PROJ-17309] Add subscription cancellation export automation`. For a single logical change one commit is correct; if the diff spans clearly separate concerns, tell the user you recommend splitting and let them decide.
- **The pre-commit hook runs automatically here** (if installed via `npm run hooks:install`). It checks staged `*.cy.js` for syntax (CJS or ESM) + the no-5xx rule + no NEW ambiguous 2xx/4xx `oneOf` on added lines (escape hatch: `// status-ambiguous: <reason>`), and validates touched JSON. **If the hook fails, the commit is rejected — stop, show the hook output, and do NOT push.** Fix the reported issues and re-run `/pr`. Do not use `--no-verify` to bypass it.
- **Do NOT add a `Co-Authored-By` or "Generated with" trailer to the commit message.**

## GitHub PR Creation Commands

```bash
# Branch-first guard — refuse to commit on the default branch
BRANCH=$(git rev-parse --abbrev-ref HEAD)
[ "$BRANCH" = "main" ] || [ "$BRANCH" = "master" ] && { echo "On $BRANCH — create a feature branch first"; exit 1; }

# Stage + commit (only if there are uncommitted changes). The pre-commit hook gates this.
if [ -n "$(git status --porcelain)" ]; then
  git add -A
  git commit -m "[PROJ-XXXXX] Example title"   # reuse the PR title; hook runs here
fi

# Check if branch exists on remote
git ls-remote --heads origin "$(git rev-parse --abbrev-ref HEAD)"

# Push branch with upstream tracking if needed
git push -u origin "$(git rev-parse --abbrev-ref HEAD)"

# Create PR — default base is main
gh pr create --base main --title "[PROJ-XXXXX] Example title" --body "$(cat <<'EOF'
## Summary

- ...

## Modules Affected

- ...

## Test plan

- [ ] ...

Refs: PROJ-XXXXX
EOF
)"

# Open or print the created PR
gh pr view --web
```

## Error Handling

- If `gh` CLI is not installed or unauthenticated, tell the user to install/auth (`brew install gh` then `gh auth login`) and stop — do not attempt to push.
- If the current branch is `main`/`master`, stop and ask the user to branch first (branch-first guard) — do not commit.
- **If the pre-commit hook rejects the commit**, stop immediately, show the hook output, and do not push or open a PR. The user must fix the flagged spec(s)/JSON and re-run `/pr`. Never bypass with `--no-verify`.
- If the branch is not on the remote, push it (after user confirmation in step 3).
- If parent-branch detection fails, ask which branch to target — do not guess.
- If `gh pr create` fails, show stderr and offer the rendered title/body so the user can create the PR manually.
- If the user declines to create the PR, output the generated content as a final block they can copy.
